# FloodGuard M4 — Landslide Hazard Estimate (prototype)

> **TRAINED ON A SYNTHETIC LABEL — NOT REAL LANDSLIDE EVENT DATA.**
> There is no landslide inventory in this repo, and no land_cover/geology
> columns in the M3 mock dataset. Both are generated by a documented rule
> (see "Where the training data comes from" below). Treat
> `landslide_probability` / `risk_level` as a rough context signal for the
> dashboard, never as ground truth or as input to the M3 flood model.

## What this is

M4 is an **independent supporting hazard module**, structurally the same
shape as M1/M2/M5. It does not feed the M3 flash-flood probability in any
way — `runM3Prediction()` in `server.js`, `services/zoneEngine.js`, and
`services/alertEngine.js` never call anything in `ml/m4/` or
`routes/m4.js`, and nothing M4 writes is read back by M3. It exists
solely to drive the M4 card on the Overview dashboard with a separate
hazard signal, clearly labeled as context.

## Pipeline

```
        ml/data/M3_train.csv / M3_validation.csv / M3_test.csv
   (M3's mock dataset — slope_deg/elevation_m/rainfall/soil_moisture
    columns reused as inputs; M4 never reads flash_flood_next_3h or
    any water-level column)
                             │
                             ▼
                ml/m4/train_landslide.py
  1. assign_terrain(): derives land_cover/geology per station,
     deterministically, from that station's own slope_deg/elevation_m
     (stand-in for a real GIS terrain lookup this prototype lacks)
  2. landslide_risk_score(): a documented weighted rule over
     normalized slope, soil moisture, 24h rainfall, and the
     land_cover/geology terrain-risk factor, plus small Gaussian
     noise, thresholded to a binary landslide_synthetic_label
  3. trains one RandomForestClassifier + sigmoid calibration
     (same FrozenEstimator pattern as train_m3.py)
                             │
                             ▼
   ml/artifacts/M4_random_forest.joblib, M4_calibrated_model.joblib,
                    M4_model_metadata.json
     ml/reports/M4_training_report.md, M4_metrics.json,
              M4_{train,validation,test}_predictions.csv
                             │
                             ▼
                ml/m4/predict_landslide.py
        (JSON features in on stdin → JSON hazard estimate out on
         stdout, same contract as ml/scripts/predict_m3.py)
                             │
                             ▼
                     routes/m4.js
   builds a feature vector for a location from whatever DB history
   exists (locations, terrain_features, rainfall_readings,
   soil_moisture_readings), falling back to neutral defaults (and the
   lowest-risk terrain class) for anything missing
                             │
                             ▼
          GET /api/m4/hazard?location_id=...
                             │
                             ▼
                 M4 card on the Overview dashboard
```

## Files

| File | Purpose |
|---|---|
| `train_landslide.py` | Loads the M3 CSVs, synthesizes land_cover/geology and the landslide label, trains + calibrates the model, and writes artifacts/reports. Run with `python ml/m4/train_landslide.py`. |
| `predict_landslide.py` | Core inference script: JSON features in, `{landslide_probability, risk_level, model_version, data_is_synthetic}` out. No DB access, no network — same "pure function" shape as `ml/scripts/predict_m3.py`. |

`../../routes/m4.js` (Node) lives outside this folder — see its file
header for the DB/query side.

## Where the training data comes from

The M3 mock dataset has real (mock) `slope_deg`, `elevation_m`,
`rainfall_1h..24h`, and `soil_moisture` per station, but no
`land_cover`/`geology` columns and no landslide-event column at all. Two
things are synthesized in `train_landslide.py`, both rule-based and fully
deterministic (no unreproducible randomness):

1. **`land_cover` / `geology`** — `assign_terrain()` derives them purely
   from a station's own `slope_deg`/`elevation_m` (steeper slope ->
   `sparse_vegetation`; higher elevation -> `fractured_metamorphic`;
   etc.). This stands in for a real GIS land-cover/geology lookup.

2. **`landslide_synthetic_label`** — `landslide_risk_score()` combines
   normalized slope, soil moisture, 24h rainfall, and a land_cover/geology
   risk factor, plus Gaussian noise, thresholded at a fixed cut chosen to
   land near an ~11% positive rate (landslides are rare events). Exact
   weights, normalization constants, and the threshold are in
   `train_landslide.py` and echoed into `M4_model_metadata.json` under
   `label_rule` for anyone auditing a prediction.

This does not reflect real landslide susceptibility science with any
precision. It exists so the pipeline (train -> artifacts -> inference ->
API -> dashboard) can be built and tested end-to-end.

## Running it directly

```bash
python -m pip install -r ml/requirements.txt
python ml/m4/train_landslide.py
```

```bash
echo '{"slope_deg":22,"elevation_m":1800,"land_cover":"sparse_vegetation","geology":"fractured_metamorphic",
       "rainfall_1h":5,"rainfall_3h":12,"rainfall_6h":30,"rainfall_12h":55,"rainfall_24h":90,
       "soil_moisture":70,"moisture_change_3h":8}' \
  | python ml/m4/predict_landslide.py
```

```json
{"model_version": "M4-v1.0", "landslide_probability": 0.8957, "risk_level": "EXTREME", "risk_meaning": "Very high hazard signal on this synthetic model — treat as context only", "data_is_synthetic": true}
```

`land_cover`/`geology` are optional in the request — if omitted or
unrecognized, `predict_landslide.py` falls back to the lowest-risk class
in each encoding (`forest` / `sedimentary`) rather than failing.

## API

```
GET /api/m4/hazard?location_id=...
```

```json
{
  "location_id": 1,
  "place_name": "Chamoli",
  "landslide_probability": 0.14,
  "risk_level": "LOW",
  "risk_meaning": "No strong landslide-hazard signal from M4",
  "model_version": "M4-v1.0",
  "data_is_synthetic": true,
  "data_quality": "estimated",
  "generated_at": "2026-09-08T09:20:00.000Z"
}
```

`data_quality` is `"measured"` only when the location has a
`terrain_features` row (with both `land_cover` and `geology` set) and a
recent `rainfall_readings` / `soil_moisture_readings` row. Most locations
don't have rainfall/soil-moisture ingestion wired up yet (see
`db/schema.sql` — no ingestion job populates those tables in this MVP)
and may have no `terrain_features` row at all. Rather than fail, the
route substitutes neutral baseline values (and the lowest-risk terrain
class) for whatever is missing and reports `"estimated"` so the frontend
never presents a guess as a real reading — same spirit as M1/M5's
`quality_status` / `data_quality`.

## Why this is safe alongside M3

Same mechanism as M1/M2/M5: M4's route, model, and artifacts are entirely
separate files (`M4_`-prefixed in `ml/artifacts/` and `ml/reports/`, a
dedicated `ml/m4/` folder, a dedicated `/api/m4` mount in `server.js`).
Nothing in `runM3Prediction()`, `services/zoneEngine.js`, or
`services/alertEngine.js` was changed, and none of them import from
`ml/m4/` or call `/api/m4/hazard`. M4 is additive only, and the dashboard
card explicitly labels it as a separate signal from the M3 flood
probability.
